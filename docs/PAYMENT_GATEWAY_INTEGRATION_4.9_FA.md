# قرارداد اتصال درگاه هر فروشنده — آماده‌سازی ۴.۹، نه اتصال عملیاتی

## مرزبندی امنیتی

`lib/digital-payments.js` یک دفتر داخلی با دو تابع `createIntent` و `verifyIntent` فراهم کرده است. **هیچ‌کدام از این توابع از HTTP عمومی فراخوانی نمی‌شوند.** از یک توکن نمایشی، فرمی که کاربر پست کرده یا callback با عبارت `success=true` نباید پرداخت تأیید شود.

پیش از اتصال واقعی، توسعه‌دهنده باید ارائه‌دهنده درگاه و مستندات رسمی همان ارائه‌دهنده، حساب اختصاصی **همان فروشنده**، مبلغ/واحد، روش امن اعلام نتیجه، API استعلام مستقل، قرارداد دریافت وجه و شرایط حقوقی فایل را بررسی کند. شناسه عمومی صرفاً برای پرونده آمادگی است؛ API key/secret باید به صورت رمز/secret manager یا متغیر محیطی خصوصی سرور نگهداری شود و در SQLite، URL، لاگ و صفحه وب ذخیره نشود.

## گردش کار پیشنهادی برای نسخه بعدی

۱. بک‌اند پس از تأیید قابلیت فروش، `createIntent(db,{digitalId,idempotencyKey})` را با درخواست با شناسه یکتای تصادفی اجرا کند؛ تابع، مبلغ **تومان** و فروشگاه/پذیرنده را از دیتابیس می‌خواند. شناسه درخواست ۱۵ دقیقه اعتبار دارد.
۲. بک‌اند با مشخصات **سروری پذیرنده همان فروشگاه**، درخواست را به API رسمی درگاه می‌فرستد و token/order ID معتبر درگاه را به intent متصل می‌کند؛ این مرحله هنوز پیاده‌سازی نشده است. درگاه ممکن است واحد ریال بخواهد؛ تبدیل تومان به ریال فقط با بررسی قرارداد همان درگاه، کنترل overflow و ثبت صریح واحد انجام شود.
۳. پس از redirect/callback، بک‌اند باید وضعیت را با **درخواست مستقل سمت سرور به درگاه** استعلام کند. برای `verifyIntent(db,intentRef,verificationRequest,verifier)`، `verifier` فقط پس از دریافت و بررسی پاسخ معتبر درگاه باید `success`, `intentRef`, `provider`, `merchantLabel`, `storeId`, `digitalId`, `amountToman`, `currency='TOMAN'`, و `transactionId` صحیح را برگرداند. هیچ فیلد دریافتی از مرورگر را به‌عنوان پاسخ معتبر جا نزنید.
۴. `verifyIntent` قیمت فعلی و مجوز PDF را دوباره می‌سنجد و فقط در همان تراکنش SQLite، رکورد پرداخت را «تأییدشده» کرده و یک دسترسی دانلود با حداکثر ۳ دریافت و اعتبار ۷۲ ساعت می‌سازد. توکن خام فقط در نتیجه همان اجرای موفق قابل دسترس است و در دیتابیس صرفاً هش نگهداری می‌شود.
۵. نمایش رسید/دریافت لینک به مشتری، وبهوک‌های دارای امضا، تلاش مجدد امن، رسیدگی به انقضا با وجود وجه پرداخت‌شده، لغو/بازپرداخت، اعتراض تراکنش و قطع دسترسی پس از برگشت وجه **هنوز باید طراحی، اجرا و روی sandbox واقعی آزموده شوند**. در ساختار فعلی هر پرداختِ تأیید‌شده بدون تحویل امن لینک در همان پاسخ می‌تواند نیازمند رسیدگی انسانی باشد؛ قبل از انتشار این بخش تکمیل شود.

## موارد مانع انتشار واقعی

- مدارک، مجوز کتاب دیجیتال و پذیرندگی مستقل فروشنده؛ کنترل‌های واقعی ضدتقلب.
- HTTPS معتبر، مدیریت secrets، لایه rate limiting و محافظت callback/webhook از جعل و تکرار.
- تست هم‌زمانی، قطعی شبکه، پرداخت موفق ولی timeout، تکرار webhook، شکست تحویل و بازگشت وجه.
- آزمایش واقعی روی گوشی و دسکتاپ و تائید UX پرداخت، سبد خرید و رسید.

هیچ آزمایش با mock، به معنی اتصال یک درگاه بانکی واقعی نیست.
